## What was implemented

The Q8 blocker was the host-side PLE table, not the GGUF parser or ordinary Q8
matrix execution:

- `src/models/qwen38_flash_next/weights.cpp`
  - permits `GgmlType::kQ8_0` for `per_layer_token_embd.weight`;
- `src/models/qwen38_flash_next/ngram.cpp`
  - accepts Q8 PLE rows using the canonical 32-value/34-byte geometry;
  - decodes Q8 rows through the existing `DequantizeQ8_0()` helper;
  - keeps the table host-side and direct-I/O backed;
- `tests/models/qwen38_flash_next/ngram_test.cpp`
  - covers 160-wide Q8 rows, unaligned offsets, cold/cached/async/batched reads,
    duplicate/interior/final rows, truncation, and invalid dimensions.

The PLE tensor is in shard 3:

```text
per_layer_token_embd.weight
shape: [320001536, 160]
type: Q8_0
row bytes: 170
encoded table size: approximately 54.4 GB
```

It is read locally by each host and is not uploaded to GPU memory.

## Current diagnosis

The most likely cause is **rank-local MoE routing-plan desynchronization**, not
expert-file corruption or a bad Q8 tensor offset:

- `Executor::Moe` computes top-k independently on each rank;
- router near-ties can differ by a ULP;
- each rank then localizes a different global expert set;
- the two ranks sum different routed contributions.

This is a hypothesis, not yet proven. The following have been checked or
ruled out:

- all six Q8 shards and the MTP sidecar have identical hashes;
- Q8 expert partition byte ranges are internally consistent;
- the Q8 MMQ kernels use explicit rounded products/FMA;
- the long request is below the 64 MiB multi-chunk all-reduce threshold;
- the failure is not explained by the C1/C2 control broker;
- **the host-side PLE gather is identical on both hosts** (see below).

## PLE gather: excluded as the cross-host differentiator

`qwen38_flash_next_ple_gather_probe` opens its own `NgramTable` and hashes the
rows the retained long prompt gathers, host-only and with no GPU. Run on both
hosts against the same 10,720-byte prompt (`sha256 185e1a52…`), stdout is
byte-identical:

```text
prompt.tokens 2054
rows.total 32864        rows.distinct 28759
rows.sha256      084c5d62562149bf9ca11c804662685a426b238a920ef6ae6fb0931a0b193d60
rows.unique.sha256 a17f993f09f2bd2765224f7fffa5a39ed0f2f371604b11a9f52f0eaf8fe3061c
content_sha256   9bb71d58a99529300bd7e7ead09d783abe2730be51d502254d7e04a8b386e784
```

Identical across three in-process passes plus a cross pass on the other read
path, on both hosts. So the two hosts tokenize the prompt identically, select
identical row ids, and dequantize those rows to bit-identical F32 through the
real `NgramTable::Open`, direct-I/O, cache and `Read`/`StartRead` paths.

**What this does and does not establish.** It rules out the PLE table and its
read path as the cross-host difference. It is a differential, not an oracle: a
decode bug present identically on both hosts would be invisible, and nothing
here exercises the PLE injection into the residual stream or the GPU path. Most
importantly it says **nothing about the router** — the tool never runs the
model, so the routing hypothesis is not confirmed, only no longer competing with
a PLE explanation.

Two incidental corrections: the PLE tensor lives in shard 3
(`split.no=2`, confirmed by parsing the GGUF headers and by the probe's own
region report), and the prompt is 2054 tokens here rather than the ~2055 quoted
above, because the probe tokenizes the file bytes verbatim with no chat
template. Neither affects the differential.
